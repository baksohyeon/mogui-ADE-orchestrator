`product-path-guard.sh` denied a `cd` target as unresolvable in two ordinary shapes: a redirection inside the same segment (`cd <dir> 2>/dev/null && ...`, which tokenizes the redirection operator off into its own tokens) and a command on the next physical line (`cd <dir>` followed by a newline then another command, since the tokenizer treated the newline as plain whitespace and merged both lines into one segment). Both now resolve: a redirection operator and its target are dropped from the `cd` operand count before counting, and a newline ends a segment the same way `;` does, so each line is checked on its own. A `cd` into a product root still denies, whether reached through a redirection-bearing segment or a later line, and a redirection target that itself resolves into a product root still denies with the existing redirection reason.

A second pass closed four gaps the first round left open. A spaced digit before a `cd` redirection operator (`cd /outside 2 > /dev/null`) was dropped from the operand count as if it were a file descriptor attached to that operator, letting the guard's modeled directory move outside a product root while a real shell, rejecting the same `cd` as a two-target command, stays inside it; the digit is now sentinel-marked before lexing only when it is lexically attached to the operator in the source text, so a spaced digit still counts as a second operand and the `cd` still denies. A `cd` redirection target containing `$`, a backtick, a glob character, or a `~` not followed by `/` reached the guard as literal text and resolved outside a product root even though a real shell would expand it to a path inside one; such a target is now denied before any resolution. An unquoted `#` comment let the lexer's own comment handling swallow the line's closing newline along with the next physical line, silently turning that next line's command into extra arguments of the commented one; the comment is now stripped up to, but not through, its newline before lexing. A `cd` segment's input redirection (`<`, `<&`, `<<<`) was still counted as an unresolved operand even though it only reads; it is now dropped from the operand count without a product-root check on its target.

A third pass closed a gap the second round left open. A `cd` segment carrying a redirection, output or input, advanced the guard's modeled directory to the `cd` target unconditionally, even though a real shell resolves that segment's own redirection before running the `cd` builtin and aborts the move when the redirection target cannot be opened; a later relative write then resolved against a directory the shell never actually entered and landed inside a product root undetected. The assignment to the modeled directory is now conditional on the segment carrying no redirection at all, so a `cd` whose redirection target cannot be opened leaves the modeled directory where it was, and a write that follows still resolves against the real, unchanged location.

A fourth pass closed a gap the third round left open in fail-closed mode. The legacy denial for entering a product root only fires when fail-closed mode is off, so when it is on, a redirection-bearing `cd` into a product root passed unmodeled: the third round keeps the guard's modeled directory outside the root for that shape, while a real shell still moves into it, since an output redirection to a path like `/dev/null` does not stop the move. A relative write right after then resolved against the real, inside location while the guard still checked it against the stale, outside one. A `cd` segment that carries a redirection and whose target resolves under a product root now denies in every mode, right after the target is computed.

A fifth pass closed two gaps a review found in the fourth round. A `cd` segment's own input redirection target was dropped from the operand count with no expansion check at all, even though bash expands that target the same way it expands an output target before opening the file; both kinds of target now go through the same expansion refusal, and the product-root write check stays on the output target alone. A `cd` operand itself can also carry an expansion character that the guard's own path resolver reads literally; since bash expands that operand before the `cd` builtin ever runs, such an operand now denies with the same message as a malformed operand count, in every form, with or without a redirection on the same segment.
