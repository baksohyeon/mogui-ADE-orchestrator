mogui-ADE-orchestrator는 실제 레포지터리, 터미널, 후속 세션을 다루며 장수명 AI 엔지니어링 작업을 조율하는 세션 레벨 오케스트레이션 하네스입니다.

# 개요

대부분의 코딩 에이전트는 하나의 레포지터리, 하나의 터미널, 하나의 컨텍스트 창 안에서 가장 잘 동작합니다. 워크스페이스 오케스트레이션은 다른 문제입니다. 마스터 세션은 활성 트랙을 기억하고, 작업자를 격리해 파견하고, 결과를 검증하고, 컴팩션을 견디고, 필요할 때 깨끗한 후속 세션으로 제어를 넘겨야 합니다.

mogui-ADE-orchestrator는 Orca ADE 위에서 그 오케스트레이션 레이어를 담당합니다. 이 레포지터리는 모델 API를 직접 호출하지 않으며, 프로세스 내부 에이전트 프레임워크도 아닙니다. AI 에이전트 세션, git 레포지터리, 터미널, 운영 기록, 승인 게이트, 승계 기록을 관리합니다.

## 문제

하나의 코딩 에이전트 세션도 많은 일을 조율할 수 있습니다. 그러나 다중 레포지터리 워크스페이스에서는 세 가지 문제가 두드러집니다.

컨텍스트가 작업보다 먼저 소진됩니다. 요약은 도움이 되지만, 역할 상태와 승인된 결정, 활성 작업이 모두 살아남았다는 증거는 아닙니다.

세션 상태는 휘발됩니다. 충돌, 수동 초기화, 컴팩션, 오래된 터미널 때문에 다음 세션이 일부 상태만 들고 시작할 수 있습니다.

위임에는 감독이 필요합니다. 작업자 세션을 시작하는 것은 쉽지만, 어떤 계약이 파견됐는지, 어디서 실행됐는지, 어떤 증빙이 돌아왔는지, 마스터가 독립적으로 수락했는지까지 추적해야 합니다.

이 문제들은 Polsia 워크스페이스에서 구체화됐습니다. 제품 작업은 계획, `polsia-api`, 프론트엔드, `polsia-ops` 레포지터리를 가로질렀고, API 계약 변경은 레포지터리 경계를 넘어 전파돼야 했으며, 장수명 세션은 작업이 끝나기 전에 컨텍스트 한계에 가까워졌습니다. 별도의 실패 모드는 감독 없는 작업자에서 나왔습니다. 작업자는 완료를 주장하거나, 실제로 받은 적 없는 지시를 반복하거나, 의도한 리뷰 레인 밖의 체크아웃을 건드릴 수 있으므로 마스터는 보고를 주장으로 취급하고 외부 증빙을 요구해야 했습니다.

하네스는 이 실패들이 함께 나타나기 때문에 필요합니다. 같은 트랙이 하나의 세션보다 오래 지속된다면 컨텍스트 지속성, 레포지터리 라우팅, 작업자 파견, 증빙 리뷰, 승계는 서로 독립된 편의 기능이 아닙니다.

## 접근

이 레포지터리는 마스터를 영원히 살아 있어야 하는 단일 프로세스가 아니라, 장수명 운영 역할로 다룹니다.

마스터 세션은 계획, 작업 분해, 리뷰, 수락, 레포지터리 간 조율을 맡습니다. 작업자 세션은 좁은 계약을 받고 산출물과 증빙을 돌려줍니다. 마스터는 독립 검증 뒤에만 수락합니다.

운영 상태는 채팅 밖의 지속 저장소로 승격됩니다. 실행 상태는 이슈 트래커나 원장에 둡니다. 장기 절차, 결정, 런북, 계보는 git 문서에 둡니다. 채팅 컨텍스트는 유용하지만 유일한 정본은 아닙니다.

승계는 명시적 절차입니다. 현재 마스터는 얇은 핸드오프를 만들고, 깨끗한 후속 세션을 스폰하고, 후속 세션이 상속 상태를 복구했는지 확인한 뒤, 이전 세션을 은퇴시킬 수 있습니다. 권고 신호는 승계를 제안할 수 있지만, 현재 구현은 명시적 트리거 없이 자동으로 마스터를 승계하지 않습니다.

> 참고: 공개 문서는 제어 모델을 설명합니다. 호스트별 배선, 워크스페이스별 경로 정책, 민감 레인 구현은 이 공개 표면 밖에 둡니다.

## 도입 기준

이 설계는 두 가지 이상의 압력이 함께 나타날 때 값어치가 있습니다. 트랙이 단일 세션보다 오래 지속되거나, 하나의 작업이 `polsia-api`와 `polsia-ops` 같은 여러 레포지터리에 걸치거나, 여러 작업자가 동시에 실행되거나, 프로덕션에 닿는 권한을 다룰 때입니다. 이런 경우 원장, 얇은 핸드오프, 작업자 lease, 증빙 묶음, 승인 게이트, 복구 경로가 반복 설명을 줄이고 수락을 감사 가능하게 만듭니다.

반대로 하나의 레포지터리에서 하나의 에이전트로 짧게 끝나는 작업에는 과할 수 있습니다. 그 경우 레포지터리 지시 파일, 이슈 트래커 항목, 최신 세션 요약으로 충분할 수 있습니다. 가장 작게 가져갈 규칙은 세 가지입니다. 정본을 채팅 밖에 두고, 승계를 정상 생애주기로 다루며, 에이전트의 자기 보고를 완료 증빙으로 쓰지 않는 것입니다.

## 핵심 기능

실행 환경: Orca 관리 터미널과 git worktree가 실제 실행 경계입니다. 어댑터 레이어는 작업자가 체크아웃을 공유해도 되는지, 별도 worktree가 필요한지 판단할 수 있습니다.

컨텍스트 관리: 부트스트랩 코드는 제한된 L0/L1 컨텍스트 블록을 적재하고, Role State를 파싱하며, 가능한 경우 이슈 트래커 메모리 요약을 감사하고, 컴팩션 전용 회상 프로브를 포함합니다.

위임: 파견 게이트는 `check -> dispatch -> register` 흐름을 따릅니다. 읽을 수 있는 작업자 계약을 파견 전에 검사하고, 작업 ID 검증 프로브가 통과한 뒤에만 작업을 등록합니다.

스티어링: 운영 규칙은 `Proposal -> Approval -> Execution`입니다. Role State는 마스터가 수행할 수 있는 작업 종류를 제한하고, 중요한 수락에는 분리된 리뷰 렌즈를 사용할 수 있습니다.

파일시스템 모델: 이 프로젝트는 virtual filesystem을 제공하지 않습니다. 대응 개념은 레포지터리 레벨 격리입니다. 경로 해석, 레포지터리별 worktree, 민감 레인을 일반 구현 작업과 분리하는 운영 규율이 여기에 해당합니다.

## 관련 작업

[LangChain Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview)는 에이전트 애플리케이션 내부에서 비슷한 신뢰성 문제를 다룹니다. LangGraph 런타임 위에 놓인 고수준 추상화이며, 실행 환경, 컨텍스트 관리, 위임, 스티어링, virtual filesystem 접근을 기본 기능으로 제공합니다.

mogui-ADE-orchestrator는 다른 층위에서 동작합니다. Deep Agents가 프로세스 안에서 실행 그래프를 배선한다면, 이 프로젝트는 실제 에이전트 세션, 검증 단계, 작업자 계약, git 체크아웃, 터미널 배치, 승계 루프를 운영 규율과 스크립트 진입점으로 배선합니다. 문제 공간은 겹치지만 제어 평면은 다릅니다.
