# Defense inventory

What stands between this runtime and the failure modes it has already paid for. Every row names a path that exists in the tree; if a claim cannot open a file, it does not belong here. This page expands the README section "What is standing guard".

| Guard | What it prevents | Where it lives | Measurement that proves it | Breaks when |
| --- | --- | --- | --- | --- |
| Dispatch gate with tier × fan-out caps | Silent cost blowups: a top-tier model fanned out across many workers, or the same count one dispatch at a time | `scripts/dispatch-gate`, `src/master_runtime/core/dispatch_gate.py`, `master-ops/model-tier-policy.json`; procedure in `master-ops/docs/MASTER-OPERATIONS.md` §5 | `check` returns a `GateDecision` with a stable reason (`TIER_FANOUT_CAP` when over the window). Policy version 2 and later apply a per-tier cap on agents accumulated in a rolling window; overrides require `--tier-override` and are ledgered. Replay: ten agents at a top tier must deny, and so must ten sequential single-agent dispatches (`MASTER-OPERATIONS.md` §9, "Put the guard where the incident was") | Policy file is unreadable, supplied with `--tier-policy` flag does not exist, or policy JSON is malformed; `check` returns a deny decision with reason `TIER_POLICY_UNAVAILABLE`, which is printed and ledgered like any other verdict |
| Ledgered gate decisions (policy path + `sha256`) | An unverifiable "the gate allowed it" with no record of which policy decided | Same gate writes JSONL via `--ledger` (default under the gate config); `dispatch-gate report` aggregates | Each decision records the policy path, `tier_policy_sha256`, and tier spent. `report` lists every policy a span was judged against; more than one policy row means the span was not judged against one policy | Ledger path is not writable, or the path points outside the repository; attempts to append exit 2 or fail silently depending on permissions |

Exit 2 means undecidable — never read as a pass. Status lines are explicitly not evidence | Session transcript file format changes, location moves, or host session storage is unreadable; probe prints `MODEL-PROBE DRIFT:` and exits 2 rather than returning a model identifier |

Three-set: host selector, process cwd under workspace root, session artifact in the expected namespace. Measured misplacement 2026-08-03 | Expected placement argument is wrong, process runs outside workspace root, or session artifact location cannot be measured; spawn exits 26 (`SPAWN_PLACEMENT_MISMATCH`) instead of proceeding |

| Duplicate master detection (runtime) | Two live masters after succession or resume | `scripts/master-succeed check-duplicates` (`src/master_runtime/core/succession.py` `detect_duplicate_instances`) | Marker scan excluding `--self-handle`; non-empty result is a finding, not a soft warning | Required handle or marker argument is missing, or Orca session introspection is unavailable; detection raises `SuccessionError` with exit code 2 rather than scanning silently |
| Redaction scan that states its scope | A green scan that only covered generic patterns while organization rules were missing | `scripts/redaction-scan.sh`; organization rules via `REDACTION_EXTRA_PATTERNS`; require with `REDACTION_REQUIRE_EXTRA=1` | Prints coverage (files/rules). Exit 0 clean, 1 findings, 2 cannot decide. With `REDACTION_REQUIRE_EXTRA=1`, missing or empty extra rules exit 2 instead of scanning generics only (`MASTER-OPERATIONS.md` §9, "A green light must name its scope") | `REDACTION_EXTRA_PATTERNS` file does not exist or is empty when `REDACTION_REQUIRE_EXTRA=1`; scan exits 2 (cannot decide) and prints coverage so the constraint is visible in the output |
| Redaction inventory (inverse of the scan) | Rules that never mention the tokens that actually appear in the tree | `scripts/redaction-inventory` | Exit 0 no uncovered candidates, 1 candidates found (normal finding, not a secret verdict), 2 cannot decide. | Revival checks for frozen sessions | Retired masters revived from another device (phone, remote terminal) while the current master assumes the seat is empty | `master-ops/docs/runbooks/succession-boot-card.md` (Retirement Completion And Revival Checks); also noted in `docs/public/orca-concepts.md` | Retirement complete only when process, pane, and tty are measured gone. Boot (and on owner report) scans running agent processes for session ids recorded in lineage; on hit: recover owner instructions, terminate process, hang up tty chain, confirm gone. Measured: four retired masters revived at once by mobile resume | Lineage session ids are not recorded, process introspection is unavailable, or session is revived on a different machine where recorded ids do not exist; detection cannot prove session was revived and boot completes anyway (degradation) |

## Substrate and stability

Guards in this table stand on two kinds of substrates. **Contracted surfaces** include this repository's own scripts and exit codes, `git`, and documented Orca subcommands (`orca terminal list`, `orca status`). Changes to these require changes to this repository. **Vendor-internal formats** include host session-file storage layout, location, and naming — formats that are neither contracted nor versioned. When a vendor-internal surface changes, guards depending on it degrade: model probes print `MODEL-PROBE DRIFT:` and exit 2 instead of returning a model identifier, revival checks exit 2 instead of scanning, and dispatch registrations surface as `MODEL_PROBE_FAILED` or similar recorded warnings. These degradations never surface as false passes. On 2026-08-03, a newly created grok worker's first `register` call returned `MODEL_PROBE_FAILED` when the session file did not yet exist at the expected path; the ledger recorded the dispatch as unverified, and the system recorded the degradation rather than pretending verification succeeded. This is the intended behavior: transparency when a substrate is unreachable, not a silent fallback.

## How to use this page

- **Operators** read the README section first; open a row here when you need the script name, the exit code, or the incident that paid for the rule.
- **Agents** treat paths as the authority. Do not invent a guard that is not in this table; if you find a real guard missing a row, add it with a path and a measurement, or drop the claim.
- **Sources for this table:** `master-ops/docs/MASTER-OPERATIONS.md §3, §5, §9; `master-ops/docs/runbooks/succession-boot-card.md`; `scripts/` entry points; `master-ops/onboarding/09-spawn.md` and `master-ops/ONBOARDING.md`; public notes in `docs/public/orca-concepts.md` and `CHANGELOG.md` / `master-ops/CHANGELOG.md` for dated incidents.

## Not in this inventory

Preferences, optional skills, and tools that help but do not gate a dangerous action. Those live in the README tool tables and in onboarding Step 7. A gate nobody can fail is not a defense; a measurement nobody runs is not a proof.
