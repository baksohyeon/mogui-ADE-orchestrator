## 3. 관측 공백

- `gh api graphql`로 pullRequest의 `reviews`와 `reviewThreads`를 병합 전에 한 번도 재조회하지 않음 — 쳤다면 16:00:46Z 리뷰가 보였다.
- cubic이 check는 pass로 주면서 findings를 리뷰 코멘트로 남긴다는 이원 표면을 측정하지 않고 check pass = 리뷰 무결로 등치했다.
- 워커 측정의 **시각**을 기록만 하고 유효기간 개념 없이 소비했다.

## 4. 실패 분해

- 건너뜀: 병합 직전 재측정 단계 자체가 내 절차에 없었다.
- 잘못된 추론: "체크 전부 pass + 워커가 스레드 0 측정 = 리뷰 관문 통과" — 측정의 신선도와 리뷰 표면의 이원성(check vs 리뷰 코멘트)을 무시한 등치.
- 수습이 더 나빠질 뻔한 지점: 스쿼시 여부까지 의심받았다 — 병합 기록을 내가 먼저 제시하지 않아 오너가 직접 확인해야 했다.

## 5. 변명 처형

- "체크가 다 초록이었다" → [관측] cubic 리뷰는 check pass와 동시에 P1 findings를 리뷰 코멘트로 제출했다. check 표면은 리뷰 본문 표면이 아니다 — 내가 이번 주에 직접 문서화한 reading-surface 독트린 그대로. 기각.
- "워커가 스레드 0을 측정했다" → [관측] 그 측정은 cubic 제출 **전**이다. 낡은 측정을 신선한 것처럼 소비한 건 측정을 안 한 것과 같다. 기각.
- "12분은 짧다" → [관측] 봇 리뷰는 push 직후 수 분 내 제출되는 게 상례이고, 병합 전 재조회 한 줄이면 잡혔다. 비용 1초 vs 손실 P1 2건 본선 유입. 기각.

## 7. Roast

reading-surface 독트린을 같은 주에 자기 손으로 쓴 자가, "창구가 아니라 실체를 읽어라"의 정확히 반대를 본선 병합에서 실행했다. 병합은 이 하네스에서 가장 되돌리기 비싼 행위인데, 가장 싼 검증(재조회 한 줄)을 생략했다. 워커에게는 "측정 시각을 명시하라" 요구하면서 정작 마스터는 측정 유효기간 개념 없이 소비했다 — 규칙이 아랫사람용이었던 셈이다.

## 8. 재발방지

1. 트리거: 모든 `gh pr merge` 실행 직전 → 볼 신호: 그 자리에서 `gh api graphql`로 pullRequest의 `reviews.nodes.submittedAt`와 `reviewThreads.nodes.isResolved` 재조회, 최신 리뷰 submittedAt > 직전 측정 시각이면 본문 전부 읽음 → 실패 시: 병합 중단. (pr-house-rules v3에 등재 완료)
