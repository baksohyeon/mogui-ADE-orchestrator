작업자 계약이 게이트를 통과하고, 작업자 job이 등록되고, 마스터가 결과를 독립 검증한 경우에만 위임을 수락합니다.

# 위임과 리뷰

마스터는 작업을 조율하지만 모든 구현과 리뷰를 직접 수행할 필요는 없습니다. 다만 위임은 추적 가능할 때만 유용합니다. 이 레포지터리는 계약 게이트, job 등록, 증빙 요구, 독립 수락을 사용합니다.

## 작업자 파견 게이트

감독된 흐름은 다음과 같습니다.

```text
check -> dispatch -> register
```

`check`는 작업자 계약을 읽고 파견 원장에 결정을 기록합니다. `dispatch`는 어댑터를 통해 작업자를 시작하거나 계획합니다. `register`는 작업자 job id가 예상 산출물에 나타난다는 프로브가 통과한 뒤에만 유효합니다.

게이트는 정책이 실행 경로에 배선되지 않으면 쉽게 우회되기 때문에 존재합니다. 한 작업자 실행 경로는 예상한 경고 경로 밖에서 실행됐고, 경고가 없다는 사실이 잘못해서 허가처럼 취급된 적이 있습니다. 이후에는 모든 작업자 실행 표면을 파견 경계에 포함하고, 누락됐거나 검증할 수 없는 파견을 사후 수락하지 않고 위반으로 기록하는 방향으로 바뀌었습니다.

check 예시:

```bash
scripts/dispatch-gate \
  --ledger ./.dispatch-ledger.jsonl \
  check \
  --runtime codex \
  --contract ./contracts/job.md \
  --agents 1 \
  --est-chars 2000
```

dry-run dispatch 예시:

```bash
scripts/adapter dispatch \
  --contract ./contracts/job.md \
  --repo ./polsia-api \
  --runtime codex \
  --agents 1 \
  --est-chars 2000 \
  --ledger ./.dispatch-ledger.jsonl \
  --dry-run
```

register 예시:

```bash
scripts/dispatch-gate \
  --ledger ./.dispatch-ledger.jsonl \
  register \
  --job-id job-123 \
  --probe-cmd 'test -f ./worker-evidence/job-123.txt' \
  --runtime codex \
  --contract-sha abc123abc123
```

> 참고: 공개 문서는 로컬 라우팅 규칙이나 경고 규칙 목록을 싣지 않습니다. 게이트는 기록되는 허가 경계로 다루고, 현재 플래그는 로컬 CLI help에서 확인합니다.

## 작업자 계약 규율

작업자 계약은 다른 세션이 추측 없이 실행할 수 있을 만큼 좁아야 합니다.

계약은 관측 가능한 사실을 중심으로 씁니다.

- 대상 레포지터리와 체크아웃
- 허용된 작업 표면
- 수락 기준
- 필요한 증빙
- 커밋, push, 브랜치 규칙
- 알려진 제외 범위와 금지 편집

작업자 자기 보고는 증빙이 아닙니다. 증빙은 마스터가 직접 확인할 수 있어야 합니다. 예를 들어 diff, 테스트, 로그, 생성 파일, 결정적 프로브, 권위 있는 문서가 있습니다.

작업자가 계약을 마스터와 다르게 해석했다면 부분 결과를 그대로 수락하지 않습니다. 마스터는 lease를 바로잡고, 개정 사유를 기록하고, 재파견하거나 변경 요청을 내며, 작업자 완료와 수락을 계속 분리해야 합니다.

## 커밋 규칙

커밋 권한은 계약에 있어야 합니다. 작업자는 commit, push, deploy, 공유 파일 편집 가능 여부를 추론하지 않아야 합니다.

유용한 계약 문구는 구체적입니다.

```text
Local commit allowed. Push forbidden. Commit only files changed for this job.
Evidence file stays uncommitted.
```

커밋 권한이 없으면, 보수적으로 변경을 커밋하지 않고 정확한 상태를 보고합니다.

## 리뷰 렌즈

중요한 작업에는 운영 가이드가 세 가지 리뷰 렌즈를 권장합니다.

```text
general correctness
regression disproof
contract and scope
```

목적은 절차 자체가 아닙니다. 실패 모드를 분리하는 것입니다. 한 리뷰는 코드가 동작하는지 묻고, 다른 리뷰는 기존 동작이 유지됐는지 반증하려 하며, 또 다른 리뷰는 작업자가 계약을 지켰는지 확인합니다.

마스터는 다수 판단을 사용할 수 있지만, 심각한 소수 의견은 고치거나 증빙으로 명시적으로 기각해야 합니다.

이는 인기투표가 아니라 렌즈 분산입니다. 세 표 리뷰가 유용한 이유는 한 경로가 결과 동작을 보고, 다른 경로가 회귀를 반증하려 하며, 또 다른 경로가 계약 준수를 확인하기 때문입니다. 계약 또는 회귀 렌즈가 차단 이슈를 찾으면, 다른 리뷰가 긍정적이어도 마스터는 수락 전에 처리해야 합니다.

## 수락 게이트

수락은 작업자 결정이 아니라 마스터 결정입니다.

수락 전에 마스터는 작업자 산출물을 계약 기준으로 독립 검증합니다. 좁은 문서 작업에는 링크 검사와 redaction scan이 필요할 수 있습니다. 코드 작업에는 대상 테스트, 넓은 테스트, 직접 소스 확인이 필요할 수 있습니다. 레포지터리 여러 개를 건드리는 작업에는 각 레포지터리의 증빙이 필요합니다.

수락 게이트는 의도적으로 자기 보고를 불신합니다. "완료"는 작업자가 완료를 주장했다는 뜻일 뿐입니다. 수락은 마스터가 작업자 산출물을 lease와 연결하고, 변경 표면을 확인하고, 필요한 검증을 다시 실행하거나 확인하고, 남은 gap을 이름 붙일 수 있을 때 시작됩니다.

수락 보고서는 무엇이 통과했는지, 무엇을 실행하지 않았는지, 어떤 위험이 남았는지 적어야 합니다. 결과를 검증할 수 없다면 아직 수락된 것이 아닙니다.
