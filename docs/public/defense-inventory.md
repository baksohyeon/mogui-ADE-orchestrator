# Defense inventory

What stands between this runtime and the failure modes it has already paid for. Every row names a path that exists in the tree; if a claim cannot open a file, it does not belong here. This page expands the README section "What is standing guard".

| Guard | What it prevents | Where it lives | Measurement that proves it |
| --- | --- | --- | --- |
| Dispatch gate with tier × fan-out caps | Silent cost blowups: a top-tier model fanned out across many workers, or the same count one dispatch at a time | `scripts/dispatch-gate`, `src/master_runtime/core/dispatch_gate.py`, `master-ops/model-tier-policy.json`; procedure in `master-ops/docs/MASTER-OPERATIONS.md` §4 | `check` returns a `GateDecision` with a stable reason (`TIER_FANOUT_CAP` when over the window). Policy version 2 multiplies tier by agent count over a rolling window; overrides require `--tier-override` and are ledgered. Replay: ten agents at a top tier must deny, and so must ten sequential single-agent dispatches (`MASTER-OPERATIONS.md` §8, "Put the guard where the incident was") |
| Ledgered gate decisions (policy path + `sha256`) | An unverifiable "the gate allowed it" with no record of which policy decided | Same gate writes JSONL via `--ledger` (default under the gate config); `dispatch-gate report` aggregates | Each decision records the policy path, `tier_policy_sha256`, and tier spent. `report` lists every policy a span was judged against; more than one policy row means the span was not judged against one policy |
| Model identity from session transcripts | Trusting a declared model, or a TUI status line, while the worker ran something else | `scripts/model-identity-probe`, `scripts/model-drift-audit`; rule in `MASTER-OPERATIONS.md` §4 and §8 | Probe reads assistant model fields from JSONL (`--transcript`); drift-audit walks every assistant turn and reports transitions. Exit 2 means undecidable — never read as a pass. Status lines are explicitly not evidence |
| Model verification at `register` | Compliant `check` declarations that never match what the worker actually ran | `scripts/dispatch-gate register --model-probe-cmd`; probe reference is `model-identity-probe` | Ledger fields `model_declared`, `model_measured`, `model_verified`. `MODEL_TIER_ESCALATION` denies; `MODEL_UNVERIFIED` / `MODEL_PROBE_FAILED` warn and still register so runtimes without model reporting are not forced to turn the check off |
| Placement verification before master spawn | A master seated in the wrong worktree (repository worktree instead of workspace folder seat) | `scripts/master-succeed spawn --expected-placement`; placement three-set in `master-ops/docs/runbooks/succession-boot-card.md`; vocabulary in `docs/public/orca-concepts.md` | Spawn compares requested vs actual, then actual vs independently supplied expected placement; mismatch is exit 26 (`SPAWN_PLACEMENT_MISMATCH`). Three-set: host selector, process cwd under workspace root, session artifact in the expected namespace. Measured misplacement 2026-08-03 |
| Empty-seat gate (founding) | A second master in the same seat from a re-entered or interrupted install | `master-ops/onboarding/09-spawn.md` (seat listing must show zero terminals before spawn) | `orca terminal list --worktree <selector> --json` (or equivalent) reports zero terminals in the seat; any leftover seat-check or prior master is a hard stop |
| Duplicate master detection (runtime) | Two live masters after succession or resume | `scripts/master-succeed check-duplicates` (`src/master_runtime/core/succession.py` `detect_duplicate_instances`) | Marker scan excluding `--self-handle`; non-empty result is a finding, not a soft warning |
| Redaction scan that states its scope | A green scan that only covered generic patterns while organization rules were missing | `scripts/redaction-scan.sh`; organization rules via `REDACTION_EXTRA_PATTERNS`; require with `REDACTION_REQUIRE_EXTRA=1` | Prints coverage (files/rules). Exit 0 clean, 1 findings, 2 cannot decide. With `REDACTION_REQUIRE_EXTRA=1`, missing or empty extra rules exit 2 instead of scanning generics only (`MASTER-OPERATIONS.md` §8, "A green light must name its scope") |
| Redaction inventory (inverse of the scan) | Rules that never mention the tokens that actually appear in the tree | `scripts/redaction-inventory` | Exit 0 no uncovered candidates, 1 candidates found (normal finding, not a secret verdict), 2 cannot decide. Narrows the rules' blind spot; does not measure exposure |
| Revival checks for frozen sessions | Retired masters revived from another device (phone, remote terminal) while the current master assumes the seat is empty | `master-ops/docs/runbooks/succession-boot-card.md` (Retirement Completion And Revival Checks); also noted in `docs/public/orca-concepts.md` | Retirement complete only when process, pane, and tty are measured gone. Boot (and on owner report) scans running agent processes for session ids recorded in lineage; on hit: recover owner instructions, terminate process, hang up tty chain, confirm gone. Measured: four retired masters revived at once by mobile resume |
| Progressive onboarding load | Model overload or improvisation from reading the whole install guide at once | `master-ops/ONBOARDING.md` (router), `master-ops/onboarding/*.md` (one step file per turn) | Router forbids reading all step files at once; next file only after the current Verify list. Progressive loading is mandatory for every host and model. Measured 2026-08-03: one model drowned in the monolith, one improvised past steps (`master-ops/CHANGELOG.md`, progressive-load split / mgm-ed3) |

## How to use this page

- **Operators** read the README section first; open a row here when you need the script name, the exit code, or the incident that paid for the rule.
- **Agents** treat paths as the authority. Do not invent a guard that is not in this table; if you find a real guard missing a row, add it with a path and a measurement, or drop the claim.
- **Sources for this table:** `master-ops/docs/MASTER-OPERATIONS.md` §3, §4, §8; `master-ops/docs/runbooks/succession-boot-card.md`; `scripts/` entry points; `master-ops/onboarding/09-spawn.md` and `master-ops/ONBOARDING.md`; public notes in `docs/public/orca-concepts.md` and `CHANGELOG.md` / `master-ops/CHANGELOG.md` for dated incidents.

## Not in this inventory

Preferences, optional skills, and tools that help but do not gate a dangerous action. Those live in the README tool tables and in onboarding Step 7. A gate nobody can fail is not a defense; a measurement nobody runs is not a proof.
