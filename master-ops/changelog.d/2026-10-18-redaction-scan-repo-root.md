`scripts/redaction-scan.sh` fixed its working directory to its own repository, so a caller in another repository that ran it with `--staged` scanned this repository's empty index and read `clean` with `files=0`; measured when a gate wired this script as its staged credential lane and that lane scanned nothing while gitleaks run directly on the same staged file found the planted key. `--repo-root PATH`, or `REDACTION_REPO_ROOT` for callers that cannot pass a flag (the flag wins when both are set), names the repository to scan instead: every `git` call and every finding path is relative to it. Unset, the target stays the script's own repository, exactly as before. The gitleaks config (`config/gitleaks.toml`) keeps resolving against the script's own repository regardless of the target; a relative `REDACTION_EXTRA_PATTERNS` or `--allowlist` value resolves against the caller's own invocation directory instead, since that is where the caller typed the path. Both summary lines now carry `root=<target top level>` so a caller can see what was scanned. A target that is not inside a git work tree prints one stderr line naming the flag and the value and exits 2 before any scan, as does `--repo-root` given an empty or missing operand. Inherited `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, and `GIT_COMMON_DIR` are unset before the target is resolved, so they cannot point any `git` call at another repository.
