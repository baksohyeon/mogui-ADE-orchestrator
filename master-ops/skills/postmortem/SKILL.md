# postmortem

현재 대화 또는 지정된 증거를 바탕으로, 주니어 개발자가 진단 과정을 따라가며 배울 수 있는 트러블슈팅 문서를 작성한다. 기본 언어는 한국어다.

**무엇을 관측했고, 왜 그 명령을 실행했으며, 결과를 어디까지 해석할 수 있고, 어떤 판단을 바꾸었는지 기록한다.** 해결 여부와 원인 확정 여부는 각각 증거로 판정한다. 원인이 남아 있거나 조치가 일부만 검증된 사건도 작성할 수 있다.

## 0. 호출과 맥락 수집

인자가 없으면 현재 대화에서 다룬 디버깅 사건을 대상으로 한다. 부족한 이력은 접근 가능한 세션 색인과 관련 이슈 트래커에서 조회한다. 작성 형식, 독자, 검증 기준은 이 문서의 기본값을 적용한다. 사용자는 대상이나 기본값을 바꿀 때만 추가로 지시한다.

```
/postmortem                 현재 대화의 디버깅 사건
/postmortem <사건 이름>      여러 사건이 섞여 있을 때만 대상을 붙인다
```

조회 후에도 대상 사건이 여러 개로 남으면 사건을 식별하는 질문 하나만 한다. 호출 문장에 독자·형식·수집 범위를 반복해 적게 만들지 않는다. 그 값들은 여기에 있다.

맥락 수집원은 둘이다.

- 세션 색인. 이전 에이전트 세션의 대화·명령·실패 기록을 찾는 용도다. 색인 커버리지를 먼저 재고, 사건 시각이 커버리지 밖이면 그 구간은 색인이 침묵하는 것으로 취급한다. 침묵을 부재로 읽지 않는다.
- 이슈 트래커. 작업과 의존성, 진행 상태를 찾는 용도다. **트래커의 완료 표시는 작업 관리상의 상태이고 사건 해결의 증거가 아니다.** 해결 여부는 실행 기록과 3절의 검증 층위로 판정한다.

두 곳 모두 접근할 수 없으면 그 사실을 적고 현재 대화의 증거만으로 작성한다.

## 1. 작업 범위와 제출 모드

### 기본 계약

산출물은 마크다운 문서 하나다. `/retro`와 `/learn`이 같은 사건을 가리키면 회고와 학습 내용을 그 문서에 통합한다. 분량은 진단 과정과 학습에 필요한 만큼으로 정하며, 같은 설명과 로그를 여러 절에 반복하지 않는다.

문서화 요청을 받았을 때는 확보된 자료부터 읽는다. 기록을 채우기 위해 삭제, 재시작, 재배포, 보안 설정 변경을 다시 실행하지 않는다. 추가 조치가 필요하면 제안과 미검증 항목으로 남긴다. 사용자가 추가 진단·복구도 요청한 경우에만 그 범위에서 작업한다.

| 모드 | 선택 조건 | 이번 작업의 종료점 |
|---|---|---|
| 문서 모드 | 학습용 정리·파일 생성·대화 정리 요청. 기본값 | 파일 생성과 가능한 문서 검사. 후속 운영 반영은 상태와 인계 내용을 기록 |
| 저장소 제출 모드 | 사용자가 저장소 반영·제출을 요청하고 대상과 허용 범위가 확인됨 | 허용된 파일 반영, 게이트, 색인, 커밋·푸시를 각각 수행하고 증거 보고 |

문서 생성 요청만으로 저장소 수정·커밋·푸시 권한을 확대하지 않는다. 저장소 제출 모드에서도 쓰기 권한, 제출 브랜치, 커밋·푸시 허용 범위를 확인한다. 승인 범위가 불분명하면 해당 쓰기 단계에서만 확인한다.

필요한 정보가 현재 대화와 첨부 파일에 있으면 그것부터 사용한다. 특정 저장소나 도구의 이름이 프롬프트에 등장한다는 이유로 불필요한 원격 검색을 시작하지 않는다. 저장소 작업이 실제로 필요하면 제공된 커넥터·작업 트리의 지원 기능을 확인한 뒤 접근 가능 여부를 판단한다.

빠진 정보가 본문 작성을 막지 않으면 `<미상>` 또는 미검증으로 남기고 진행한다. 대상·안전·권한·사건 주체가 불명확하여 판단이 달라질 때만 질문한다.

### 사건 분류

- 기술 사고. 시스템·도구·외부 서비스 문제. 5절의 A 틀을 사용한다.
- 조율 사고. 마감 인식 차이, 정보 비대칭, 보고·권한·인계 문제. 6절의 B 틀을 사용한다.
- 두 갈래가 함께 있으면 기술 진단과 조율 분석을 별도 절로 나눈다. 공통 요약·시간순·예방 항목은 중복하지 않는다.

에이전트의 판단 오류도 사건에 영향을 주었다면 본문에 기록한다. 별도 blame 문서는 사용자의 요청 또는 적용되는 저장소 규약에 따라 추가 산출이 허용될 때 작성한다. 문서 하나가 계약이면 오류와 교정 내용을 같은 문서에 남긴다.

## 2. 증거 수집과 사실 보존

### 증거 대장

먼저 필요한 자료를 모으고 `E1`, `E2`처럼 식별한다. 짧은 사건은 본문 각주로 처리해도 된다.

| 증거 | 출처·실행 주체 | 관측 시점 | 원문 위치 또는 내용 | 이 증거가 보여 주는 범위 |
|---|---|---|---|---|
| E1 | 사용자 제공 CLI / 사용자 실행 | `<미상>` | 실제 명령과 출력 | 해당 명령이 조회한 상태 |

사용자가 직접 제공한 경험과 관찰은 사용자 제공 사실로 기록한다. 에이전트가 직접 실행한 결과, 사용자 실행 결과, 공식 문서, 이전 에이전트의 해석을 구분한다. 이전 답변의 단정을 원시 로그처럼 취급하지 않는다.

사용자의 현재 명시적 진술과 이전 맥락이 충돌하면 현재 진술을 우선하며, 분석에 필요한 충돌만 표시한다. 인물·사건 주체·소속·시점을 다른 사례와 합치지 않는다.

### 원문과 빈칸

- 명령, 경로, 옵션, 오류 문자열, 출력 값은 원문을 보존한다. 로그는 `text` 코드블록에 둔다.
- 필요한 줄만 보여 줄 때는 **발췌**라고 표시한다. 떨어진 줄을 이어 붙였다면 그 사실도 밝힌다. 생략 구간을 연속 원문처럼 제시하지 않는다.
- 자격증명과 민감한 값은 일관된 표식으로 마스킹한다. 읽기용 개행 정리나 제어문자 제거도 기록한다. 문체를 맞추려고 인용 원문을 고치지 않는다.
- 수집하지 않은 종료 코드, 버전, 시간, 설치 경로, PR 번호, 작성자, 피해 규모는 채워 넣지 않는다. 문자열은 `<미상>`, 숫자·날짜 필드는 `null`을 사용한다.
- 파일 수정 시각, 문서 작성일, 셸 프롬프트의 시각을 사건 발생 시각으로 바꾸지 않는다. 기본 시간대는 KST이며 원본 시간대도 보존한다.
- 환경에 접근하지 못했다면 그 사실을 적는다. 문서 생성 환경에서 실행한 검사를 사용자 장비에서 실행한 검사로 표현하지 않는다.

원문이 대화 밖에 있으면 지정된 파일·로그·저장소를 읽는다. 검색 결과가 일부만 보이면 필요한 범위를 추가로 읽는다. 사내 대화는 기존 원문 대장과 색인을 우선 확인하고, 없는 자료만 추가 수집한다.

### 외부 근거

제품 동작, 옵션 의미, 버전별 제약, 알려진 사고는 공식 문서·매뉴얼·소스 코드 등 1차 자료로 확인한다. 사용자의 현장 관측과 외부 일반 설명은 분리한다.

과거 공식 사고와 증상이 맞는다는 사실은 해당 장비의 원인 확정과 구분한다. 사건 당시 버전과 현재 권장 버전, 당시 확보한 정보와 회고 중 추가로 찾은 정보를 각각 표시한다.

출처에는 실제 확인한 경로·링크·구간을 사용한다. 파일로 내보낼 때는 일반 Markdown 링크·각주로도 추적할 수 있게 한다. 접근할 수 없는 자료의 내용을 추정하거나 출처 링크를 만들어 내지 않는다. 재확인하지 못한 기존 인용은 그 상태를 표시한다.

## 3. 가설·해석·검증 규칙

### 순서와 확신의 범위

**관측 사실 -> 당시 가설 -> 확인 방법 -> 결과 -> 가설 갱신 -> 다음 단계** 순서로 정리한다.

가설의 상태는 `확인`, `강하게 지지`, `가능성 있음`, `근거 부족`, `기각`, `미검증`처럼 구분한다. 각 상태 옆에 판단 근거를 둔다. 수치 근거 없이 확률을 붙이지 않는다.

검사하지 않은 가설은 미검증으로 남긴다. 선택하지 않은 해결책은 미선택 대안으로 남긴다. 검사를 통해 반증한 경우에만 기각으로 표시한다. 서로 다른 원인 층위를 설명하는 가설은 동시에 성립할 수 있다.

당시 세운 가설과 회고 중 떠올린 대안을 구분한다. 당시 확인 비용이 싼 순서로 살펴봤다면 그 이유를 설명한다. 실제 순서가 비효율적이었다면 그대로 기록하고, 개선할 순서는 학습 항목으로 따로 적는다.

### 결과가 보장하는 만큼만 결론 낸다

명령 실행 기록과 목표 상태의 확인 결과를 구분한다. 예를 들어 출력이 없었다는 사실만으로 종료 코드 0을 기록하지 않는다. 중간 오류 메시지 하나로 최종 상태를 확정하지 않는다. 허용한 오류에는 허용 근거와 후속 확인 조건을 적는다.

실제 출력, 기대 출력, 설명용 예시는 별도 표식을 붙인다. 나중에 조회한 종료 코드를 과거 명령의 결과로 기록하지 않는다. 빈 조회 결과의 의미는 필터·권한·접속 대상·조회 범위 안에서 해석한다.

| 검증 층위 | 확인할 질문 |
|---|---|
| 조치 반영 | 변경 요청 또는 명령이 어떻게 끝났는가? 출력과 종료 코드는 무엇인가? |
| 목표 상태 | 파일·설정·서비스 등 실제 대상이 원하는 상태가 되었는가? |
| 유지할 기능 | 보존해야 할 기능이 어떤 시험에서 동작했는가? 시험 범위는 어디까지인가? |
| 원래 발생 조건 | 재부팅·재로그인·재연결·재시도 등 원래 조건에서 증상이 다시 나타나는가? |

사건에 적용되지 않는 층위는 이유와 함께 제외한다. 필요한 층위에 증거가 없으면 미검증으로 남긴다. 일부 기능 시험의 성공을 전체 정상화나 데이터 무결성으로 확대하지 않는다.

한 번의 재시험이 통과했으면 그 조건과 횟수의 통과로 기록한다. 영구 재발 방지를 보장하지 않는다. 원인 확정과 증상 해소는 독립적으로 기록한다.

### 에이전트 판단 오류의 교정

오류가 있으면 `당시 설명 -> 근거를 넘은 부분 -> 교정한 설명 -> 교정 근거 -> 다음에 적용할 확인 규칙`을 적는다. 실제 설명 오류와 현장 시스템 문제를 구분한다.

사과나 자기평가로 내용을 채우지 않는다. 잘못된 안내로 추가 작업이 발생했다면 확인되는 범위만 기록한다. 조치 반복 기록이 있어도 중간 확인이 없으면 어느 실행이 상태를 바꿨는지 추정하지 않는다.

## 4. 작성 메타데이터

저장소 모드에서는 해당 저장소의 실제 스키마와 규약을 먼저 확인한다. 문서 모드는 다음 기본 틀을 사용하되 필요한 필드만 남긴다. `<...>`를 그럴듯한 값으로 채우지 않는다.

```yaml
---
id: postmortem-draft-<slug>
seq: null
title: "<사건 제목>"
description: "<확인된 조치·결과와 핵심 미검증 항목>"
type: postmortem
date: null
context: "<어느 작업 중 발생했는가>"
audience: junior engineers
length: step-by-step
incident_kind: technical
incident_status: verification_pending
root_cause_status: unconfirmed
publication_status: draft
created_at: null
created_by: "<미상>"
updated_at: null
updated_by: "<미상>"
last_verified_at: null
last_verified_by: "<미상>"
verification_scope: []
audit_log: []
tags: [postmortem, incident]
relations: []
code_refs: []
---
```

`date`는 이 기본 틀에서 문서의 기록일이다. 사건 발생·종료 시각은 별도로 기록한다. `last_verified_at`을 작성일로 자동 채우지 않는다. 자료 검토일을 넣는 경우 `verification_scope`에 문서 근거 검토라는 범위를 명시한다. 현장 재시험 일시와 혼동하지 않는다.

`incident_status`는 `open`, `mitigated`, `verification_pending`, `resolved` 중 실제 증거에 맞게 정한다. `root_cause_status`는 `unconfirmed`, `supported`, `confirmed`로 구분한다. `publication_status`는 `draft`, `delivered`, `committed`, `pushed` 등 실제 제출 상태를 기록한다. 문서를 작성했다는 사실로 사건을 해결 상태로 바꾸지 않는다.

정식 일련번호는 실제 목록에서 확인한다. 작성자는 저장소 모드에서 대상 저장소의 `git config user.name`을 확인하고 규약에 맞게 표기한다. 문서 모드에서는 사용자가 명시한 작성자를 사용하며, 없으면 `<미상>`으로 둔다. 호스트명·계정명·다른 환경의 Git 설정으로 추정하지 않는다.

## 5. 본문 A: 기술 사고

### 1. 사건 요약

증상, 확인된 작동 경로 또는 원인, 수행한 조치, 현재 검증 상태를 짧게 적는다. 핵심 미검증 항목을 요약에서도 보이게 한다. 가설인 원인은 가설로 표시한다.

관측된 영향과 작업 범위를 적는다. 피해 자료가 없으면 미확인으로 둔다. 영향이 없다는 판정에도 확인 근거가 필요하다.

### 2. 미리 알아야 할 것과 환경

주니어가 이후 로그를 읽는 데 필요한 개념만 설명한다. 구성요소의 역할, 요청이 이동하는 경로, 서로 혼동하기 쉬운 상태를 구분한다. 제품 소개나 일반 개론으로 넓히지 않는다.

환경에는 실제 확인한 OS·버전·실행 위치·접속 대상·권한·최근 변경을 적는다. 미확인 값도 표시한다. 비교가 필요한 경우 표나 짧은 텍스트 흐름도를 사용한다.

### 3. 증상과 관측 자료

사용자가 보고한 재현 조건, 실제 경고·오류, 초기 상태를 기록한다. 보고된 재현 빈도와 직접 시험한 횟수를 구분한다. 각 출력이 어떤 명령 또는 화면에서 나온 것인지 연결한다.

### 4. 처음 세운 가설

| 가설 | 당시 가설 / 사후 보충 | 설명하려는 현상 | 확인 방법·비용 | 결과와 최종 평가 |
|---|---|---|---|---|

`H1`, `H2`처럼 식별하고 실제로 제기된 가설만 당시 가설로 기록한다. 표의 빈칸을 채우려고 새로운 경쟁 가설을 만들지 않는다.

### 5. 진단과 판단 갱신

각 단계에 다음 내용을 순서대로 둔다. 짧은 단계는 문장을 합칠 수 있지만 판단의 연결은 유지한다.

1. **확인 질문:** 이 단계에서 무엇을 구분하려 했는가?
2. **명령과 실행 조건:** 누가, 어디서, 어떤 접속 대상과 권한으로 실행했는가?
3. **실제 출력:** 원문 또는 표시된 발췌. 출력이 없었다면 그 사실을 적는다.
4. **읽는 법:** 필요한 옵션·필드·경로·오류의 의미. 처음 등장할 때 설명한다.
5. **관측과 해석:** 어떤 가설의 어느 부분을 지지·기각했는가? 무엇은 여전히 모르는가?
6. **다음 단계와 이유:** 이 결과 때문에 어떤 확인이나 조치를 선택했는가?

에이전트 판단 오류가 있었으면 이 절의 별도 소절에서 교정 과정을 기록한다. 사후에 더 좋은 순서를 발견해도 실제 디버깅 이력을 그 순서로 다시 쓰지 않는다.

### 6. 해결과 남은 것

변경한 대상, 변경하지 않은 대상, 각각의 이유를 적는다. 실제 조치와 검토만 한 대안을 분리한다.

| 선택지 | 선택 / 미선택 / 미검토 | 선택 근거·위험·비용 | 실제 시험 여부 |
|---|---|---|---|

변경 범위를 좁힌 이유와 보존할 기능·데이터를 설명한다. 데이터를 삭제 대상으로 지정하지 않았다는 사실과 데이터 보존을 검사했다는 사실을 구분한다. 복구·롤백을 실제 수행했는지, 절차만 있는지도 적는다.

삭제·교체·재시작처럼 진단 증거가 사라질 수 있는 조치는 변경 전에 무엇을 보존했는지 기록한다. 보존하지 않았다면 그로 인해 확인할 수 없게 된 항목도 남긴다. 기록을 보충하려고 문제가 있던 구성요소를 다시 설치하거나 실행하지 않는다.

| 검증 항목 | 확인 / 미검증 / 적용 없음 | 실제 근거 | 남은 최소 확인과 성공 조건 |
|---|---|---|---|

필수 종료 확인과 더 넓은 선택적 검사를 분리한다. 미확인 항목을 모두 필수 작업으로 확대하지 않는다.

### 7. 예방과 운영 노트

예방 항목은 `P1`, `P2`처럼 식별한다. 각 항목에 적용할 절차·기본값·체크리스트·가드·테스트, 비용과 확인 방법을 적는다. 주의력이나 기억력에만 기대는 처방은 구체적인 절차로 바꾼다.

필요한 변경이 운영 가이드 한 줄이면 그 범위로 끝낸다. 상시 감시, 새 훅, 새 시스템이 필요한지 별도로 판단한다. 불필요하면 `없음(설계상)`과 이유를 기록한다.

### 8. 시간순

확보된 시각 또는 확인 가능한 사건 순서로 짧게 적는다. 대화에서 언급된 시점과 실제 발생 시점을 구분한다. 정확한 시각이 없으면 순서만 기록한다. 중요한 반복 실행과 판단 수정은 생략하지 않는다.

### 9. 승격과 다음 인계

예방과 운영 노트의 각 항목에 공통 승격 규칙을 적용한다. 운영 파일에 실제 반영됐는지와 문안만 준비됐는지를 구분한다.

### 10. 명령 모음

명령이 중요한 사건이면 `실행한 조회`, `실행한 변경`, `아직 실행하지 않은 후속 검증`으로 나눈다. 본문의 상세 설명은 반복하지 않는다. 변경 명령에는 과거 실행 이력이라는 표식을 붙인다.

독자가 지금 실행할 후속 명령에는 적용 조건, 예상 결과, 중단해야 할 다른 결과를 적는다. 파괴적 명령을 설명 없이 한 덩어리로 복사·실행하게 만들지 않는다. 현재 자료로 안전한 명령을 제시할 수 없으면 필요한 확인부터 적는다.

문서 끝에는 증거와 참고 자료를 연결한다. 실제로 사용하지 않은 참고 문헌으로 목록을 채우지 않는다.

## 6. 본문 B: 조율 사고

기술 사고의 가설·CLI 진단 틀을 억지로 적용하지 않는다. 다음 순서로 작성한다.

1. **사건 요약:** 어떤 경계에서 정보·기대·권한이 갈렸으며, 관측된 결과는 무엇인가?
2. **등장 인물과 경계:** `누구 | 소속 | 소유한 업무·결정권 | 실제로 한 일`. 인물과 소속은 제공된 사실 그대로 유지한다.
3. **양쪽 타임라인:** `시각 또는 순서 | 우리 쪽 | 상대 쪽 | 출처`. 양쪽을 같은 표에서 비교한다.
4. **정보 비대칭:** `사실 | 누가 알았나 | 누가 몰랐나 | 언제 공유됐나 | 근거`. 알았는지 확인되지 않은 경우 미상으로 둔다.
5. **갈린 지점:** 각 측의 전제와 근거를 적는다. 명시적 발언, 관측된 행동, 동기 가설을 구분한다. 에이전트의 판단 오류도 발생 위치와 교정 근거를 기록한다.
6. **결과:** 확인된 손해·추가 작업·지연. 규모를 부풀리거나 미확인을 피해 없음으로 바꾸지 않는다.
7. **처방:** 보고 시점, 인계 형식, 승인 경계, 기본값, 알림 등 변경할 절차를 적는다.
8. **검증하지 않은 것:** 사후에 상대의 인식이나 합의 이행을 실제로 확인했는지 구분한다.
9. **시간순:** 핵심 전환점만 요약한다.
10. **승격과 인계:** 공통 승격 규칙에 따라 실제 반영과 남은 승인을 기록한다.

사람의 성격으로 절차 문제를 설명하지 않는다. 무비난 원칙은 관측된 행동·발언·책임 경계를 지우는 이유로 사용하지 않는다.

## 7. 공통 승격 규칙

문서를 남긴 것과 운영을 바꾼 것은 구분한다. 예방 항목마다 다음을 기록한다.

| 예방 항목 | 집과 실제 경로 / 후보 경로 | 반영할 구체 문안 | 승인·담당 | 상태·완료 기준 |
|---|---|---|---|---|

집은 기존 운영 규칙, 개념 노트, 판정 문서, 테스트, 승인 필요한 정책 문서, `없음(설계상)` 중에서 고른다. 기존 유사 문서가 있으면 중복 문서 생성보다 그 문서의 갱신을 우선한다.

- 문서 모드. 집과 바로 옮길 수 있는 문안, 남은 승인·검증을 같은 파일에 둔다. 상태는 제안 또는 미반영이다. 제출 완료와 운영 개선 완료를 분리한다.
- 저장소 제출 모드. 허용된 집의 파일을 실제로 수정한다. 새 문서·규칙 사이를 양방향으로 연결하고, 예방 항목이 실제 반영됐는지 확인한다.
- 승인 필요 또는 도구·권한 부족. 승인 대기 또는 차단으로 기록한다. 다음 담당, 다음 행동, 완료 기준을 인계한다. 담당자가 정해지지 않았으면 `<미정>`으로 둔다.

`relations`에는 실제 존재를 확인한 관계를 넣는다. 아직 없는 후보 파일은 코드 형식 경로로 표시한다. 운영 규칙 승격은 반영 내용과 양방향 연결을 확인한 뒤 완료로 표시한다.

같은 저장소의 문서·색인·규칙 변경은 함께 제출한다. 서로 다른 저장소를 수정하면 저장소별 커밋과 반영 상태를 관리하고 연결한다. 한쪽만 반영되면 전체 승격은 미완료다. 기존 사용자 변경을 무단으로 포함하지 않는다.

## 8. 문체와 검사

### 작성 문체

한국어 서술형을 기본으로 하며, 표는 비교에, 목록은 순서와 체크리스트에 사용한다. 기술 용어는 처음 등장할 때 필요한 의미를 풀어 쓴다. 하나의 개념을 여러 비유로 반복하지 않는다.

새로 작성한 산문에는 em dash, 이모지, 인위적인 양자택일형 대조 구문, 상투적인 도입·결론, 거창한 비유를 사용하지 않는다. 실제 원문 인용과 명령·정규식·로그는 별도 검사 범위로 취급한다. 검사 결과의 발견 위치를 읽고 위반 여부를 확인한다.

### 제출 전 검사

먼저 본문의 완료 주장마다 대응하는 실제 증거가 있는지 점검한다. 핵심 검사 사례는 다음과 같다.

| 입력 상황 | 문서에 남겨야 할 판정 |
|---|---|
| 변경 명령 뒤에 화면상 출력이 없고 종료 코드를 모름 | 실행과 무출력만 기록. 목표 상태는 별도 확인 |
| 중간 명령은 오류, 최종 상태 조회는 기대값 | 오류는 그대로 기록. 최종 상태 판정은 후속 조회에 근거 |
| 특정 대상·필터의 조회만 성공 | 그 범위의 성공. 전체 기능·데이터 무결성은 별도 |
| 원래 발생 조건의 재시험 결과가 없음 | 필요한 재시험을 미검증으로 유지 |
| 공식 알려진 사고와 증상만 일치 | 원인 가설 지지. 해당 인스턴스 원인 확정은 추가 증거 필요 |
| 회고 중 새 가설·명령을 추가함 | 사후 보충·미실행으로 표시 |
| 파일만 만들었고 저장소를 수정하지 못함 | 문서 산출과 저장소 미반영을 각각 보고 |

그다음 사용 가능한 검사기로 아래 범위를 확인한다.

1. **구조:** YAML 파싱, 필요한 필드, 코드블록 닫힘, 각주 정의, 사건 상태의 일관성.
2. **문체:** 적용되는 문체 검사와 수동 검토. 기존 검사기가 있으면 사용한다.
3. **출처·링크:** 내부 링크와 파일의 실재, 각주 연결, 실제 사용한 증거와 인용의 일치.
4. **민감정보:** 자격증명·개인정보·내부 접속 정보의 노출 여부와 공유 범위.

셸 명령의 문법 검사와 실제 환경의 실행 검증도 구분한다. 명령 검사를 위해 복구 작업을 다시 수행하지 않는다. 부분 검사 통과를 전체 게이트 통과로 보고하지 않는다. 검사 도구가 없으면 실제로 수행한 수동 검토와 남은 검사만 적는다.

저장소 제출 모드는 프로젝트의 실제 게이트를 사용하고 결과·종료 코드를 확인한다. 실패 원인을 고친 뒤 다시 검사한다. 게이트를 실행할 수 없으면 차단 사유를 기록하며, 우회 제출하지 않는다.

## 9. 선택 프로필: 저장소 규약

이 절은 특정 저장소에 반영하는 요청에서만 적용한다. 값은 그 설치의 실제 규약으로 채운다. 아래 자리표시자를 그대로 두고 쓰지 않는다.

- 정식 문서: `<DOC_REPO>/<POSTMORTEM_DIR>/NNN-YYYYMMDD-<author>-<slug>.md`
- 초안: `<DOC_REPO>/<POSTMORTEM_DIR>/temp/YYYY-MM-DD-<slug>.md`
- 원문: 지정 세션 기록과 그 설치의 원문 대장. 대장에 없을 때만 추가 수집한다.
- 작성자: 대상 작업 트리의 `git config user.name` 을 확인하고 규약대로 표기한다.
- 일련번호: 실제 디렉터리의 기존 번호를 확인해 다음 번호를 배정하고, 제출 전 중복을 재확인한다.
- 색인: 그 설치가 요구하는 색인 파일을 갱신한다.
- 운영 규칙과 개념·판정 문서의 경로는 그 설치의 규약을 따른다.
- 승인이 필요한 문서(헌장, 부팅 대조 집합 등)는 오너 승인 후 수정한다.
- 훅으로 규칙을 주입하는 방식은 그 설치의 반려 이력을 먼저 확인한다.

게이트는 스크립트의 존재·옵션·실행 환경을 확인한 뒤 사용한다. 호출 형식은 설치마다 다르므로 실측한 형식을 쓴다. 실행 결과를 확보하기 전에는 통과로 기록하지 않는다.

```bash
(cd <DOC_REPO> && <GATE_PATH> --files '<대상 파일>' --profile <프로필>)
```

기본 제출 순서는 허용된 승격 반영, 게이트, 색인, 최종 변경 전체 재검사, 커밋, 푸시 확인이다. 색인이나 규칙을 나중에 수정했으면 그 변경도 검사한다.

커밋 제목 형식은 그 설치의 규약을 따른다. 문서 저장소와 운영 저장소가 분리돼 있으면 각각의 변경·게이트·커밋·푸시 결과를 따로 관리한다. 공유 브랜치에 강제 푸시하거나 무관한 변경을 묶지 않는다.

## 10. 최종 전달

파일 생성 기능이 있으면 마크다운 파일 하나를 만들고, 실제 생성된 파일의 링크를 제공한다. 파일을 만들 수 없는 환경이면 복사 가능한 마크다운 본문을 제공하고 저장되지 않았음을 밝힌다.

파일을 제공할 때 채팅에는 문서의 위치, 현재 사건 상태, 중요한 미검증, 실제 제출 범위만 짧게 적는다. 사용자가 전문을 요구하면 본문도 제공한다.

저장소 제출 모드는 저장소·브랜치·커밋 해시와 푸시 확인 결과를 보고한다. 로컬 파일 생성, 운영 승격, 게이트, 색인, 커밋, 푸시를 각각 실제 상태대로 기록한다. 수행하지 않은 단계에는 완료 표현을 붙이지 않는다.

## 11. blame-agent 와의 경계

같은 사건에 둘 다 해당하면 둘 다 쓴다. 예를 들어 조회 필터가 틀린 것은 blame 이고, 그 필터가 말없이 빈 결과를 돌려준 것은 도구의 성질이라 postmortem 이다.

| | postmortem | blame-agent |
|---|---|---|
| 대상 | 시스템·도구·외부 서비스가 낸 문제 | 에이전트 자신의 판단 오류 |
| 어조 | 무비난. 시스템과 인터페이스를 지목한다 | 자기 적발. 관측 공백을 판다 |
| 착지 | 이 문서의 제출 규칙 | 해당 저장소의 blame 경로 |

무비난 원칙은 에이전트의 오류를 본문에서 지우는 근거가 아니다. 2절의 구분(에이전트 실행 결과와 사용자 실행 결과)을 그대로 적용하고, 교정은 3절의 형식으로 남긴다.
